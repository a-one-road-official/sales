# 分離型営業エンジン：実装・検証契約

## 役割

| 領域 | 所有する情報 | 書き込み境界 |
| --- | --- | --- |
| SSOT | 主営業コンテンツ、会社・案件、手動Status、担当、次アクション、期限 | 生贄ランナーは読取のみ。人の管理セルを自動更新に含めない |
| 現行生贄 | 自動アプローチ候補、実行予約、送信処理結果 | 送信対象の供給元。SSOTの未接触行を勝手に取り込まない |
| 共通イベントモデル | company_id / event_id / 種別 / 時刻 / 証拠ID | 既存履歴を読み取り正規化。イベント単位で重複除外。営業Statusへ過去値をコピーしない |

既存の2冊、既存のStatus列、履歴は保持する。旧アーカイブは実行経路に使わない。
会社IDはSSOTの登録済みLF_lead_idが一意なら優先し、それ以外は正規化した公式候補ホストから生成する。
ID・社名・URLの矛盾は要確認。ドメイン変更／ブランド別名の自動統合は行わない。

## 候補から送信まで

1. 現行生贄の `営業リスト_Vendor` とSSOTの `営業リスト＿Factory/BPO` をヘッダー名で読み取る。
2. 生贄の行だけを対象に、SSOTを使って手動営業・製造業・既接触・商談・拒否を保護する。
3. 生贄の現在Status、SSOTの現在Status・営業履歴、send_log、outreach_engine_log、ActionLogを突合する。
4. 製造業保護はMANUAL、既接触／空欄StatusはHOLD、業種・会社URL矛盾はREVIEW。
5. 確認済み分類かつ未接触の候補だけAUTO_RESEARCH。ここでは送信を許可しない。
6. 送信ワークフローの直列実行下でソースを再確認し、永続CLAIMEDを保存して応答を確認する。
7. Playwrightによる公式サイト・フォーム確認、宛先・文面・受付条件の確認後に送信。
8. タイムアウト後は再クリック／再送しない。不明な受付結果は照合待ちとして保持する。

Vertex呼び出しは禁止。静的JSONは実運用の候補供給に使わない。
既存の直接送信API／旧単体フォーム経路には新しい実行許可オブジェクトが渡らず、送信できない。
送信許可は現行生贄・企業・公式URL・レーンに紐づく。独立した並列ワーカーからの予約は禁止。

## 手動営業の保護

- 自動パッチからStatus・接触状況・Stage・Yomi・Probability・担当・期限・次アクション・承認セルを省く。
- 読み取ったStatusを同値で再保存する処理も省く。読み取り後の手動変更を古い値で潰さない。
- 会社ID／社名／URLの既存値を自動的に置き換えない。
- 更新時に観測した会社名と直前の行の会社名を照合し、並べ替え・行ずれを検出する。
- B11/B21をヘッダー扱いする不具合、A1開始の複数行更新、引用符によるガード回避を遮断。
- 壊れた履歴は空配列として上書きしない。履歴上限超過で最古の接触を削らない。
- 古い履歴パッチは最新読取分へイベント単位でマージし、人の担当／期限／進捗を空にしない。
- 新規受付はクライアントが計算した最終行への上書きをやめ、サーバー側のINSERT_ROWSにする。

人が直接変更したStatusを取り消す処理は追加していない。履歴が残る限り、手動で未接触表示に変更しても自動送信候補には戻さない。

## 返信・商談・作業量

`sales_events.py` は共通イベントの重複排除と進捗の単調な提案を担う。
同一event_idの内容矛盾は集計から除外して確認対象とする。送信イベント数と接触企業数を分ける。
過去の `success` 文字列だけで受付成功と数えない。既存のインポート済みフォーム受付と今回の実行成功を分離する。

`sales_lifecycle.py` は取得済みGmail／Calendarオブジェクトから以下を判定する。

- Gmailの新しいスレッドでも、確認済み接触企業の送信者と一意に照合できれば返信イベントにする。
- 自動返信、送信済みコピー、帰属不明のメッセージを人の返信へ混ぜない。
- カレンダーの予定ミラーや終日ブロックはアポにしない。相手の承諾・予定状態を確認する。
- 予約、面談実施、SQLを区別する。予約だけでSQLにしない。
- SQLは新ワークブックの7条件と担当・次アクションを必要とする。
- 作業量はtask_idで重複除外し、未担当・期限不明・期限超過を明示する。

Gmail／Calendarの継続取得・共通イベントへの永続取り込み・SSOTへの商談登録は、今回の読み取り検証では接続・実行していない。
現在のコードはその判定部を含む。自動的なアポ生成～商談登録の全工程完了は主張しない。
`confirmed_booking_count` / `qualified_meeting_count` は未集計ならnull。未接続ソースを0件実績としない。

## 実データ確認（2026-09-17）

現行生贄は709データ行。SSOTは主要列に5,607データ行。
生贄だけを候補源とした保守的な照合：MANUAL 593、HOLD 111、REVIEW 5、AUTO_RESEARCH 0。
MANUALは既存SSOT分類による保護を含む。593社の実業種が独立確認されたという意味はない。
会社名とURL・業種の不整合、および過去の広すぎるFactory分類は別途証拠付き修正が必要。
旧StatusのコピーやURL推測による一括修復は実施していない。

send_logは会社名のある361,471行を読み取り、再送抑止用に会社名・URL・Statusの組合せ10,863種類へ圧縮した。
この10,863はイベント数・送信数ではない。過去履歴の削除はしていない。
193件のATTEMPTED_UNRECONCILEDは受付結果未照合の記録。190件の確定失敗という判定には使わない。

## 検証と本番反映

```sh
python -m pip install -r requirements.txt
python -m playwright install --with-deps chromium
python -m pytest -q
python workbook_sales.py --check --output workbook-preflight.json
```

最後のコマンドはSheets読取専用スコープを使い、外部送信・シート更新を行わない。
ブランチの `Workbook logical-separation verification (read only)` が実行IDと集計を残す。
生贄ワークフローのデフォルトはpreflight。executeは明示選択時のみ。

残る本番受入条件：

1. 実行サービスアカウントによる両ブックの読取成功。
2. 顧客名・URL・業種が一致する自動候補の整備。曖昧な会社は保留を維持する。
3. 本番に紐づくApps Script／別サービスのStatus書込・トリガーの棚卸し。リポジトリ外のコードは未検証。
4. Gmail／予約カレンダーから返信・予約を取得し、取消・再予約・担当／期限まで通した結合検証。
5. 手動の高度な並べ替えと自動の証拠列更新の競合。Sheetsには値の比較付き原子的更新がないため、営業中はフィルタビューを使い、証拠列書込は直列化する。
6. 取得済み候補・送信件数の達成と、実際の有効商談創出を分けて評価する。

この修正は事故防止と論理分離の基盤を改善する。現在のデータ品質・未接続の返信予約処理まで含めて、商談生成マシンとして本番合格とはまだ判定できない。
